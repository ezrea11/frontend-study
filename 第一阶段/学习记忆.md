我对 125 Valid Palindrome 的当前理解：

\- 这是头尾双指针

\- `left` 从左边开始，`right` 从右边开始

\- 题目要求忽略大小写、跳过非字母数字字符

\- 所以每轮流程是：

1. 左边跳过无效字符
2. 右边跳过无效字符
3. 两边转小写比较
4. 不相等就 `return False`
5. 相等就左右继续向中间移动

\- 外层循环条件是 `left < right`

\- 如果整个循环顺利结束都没出错，最后 `return True`



我在 125 里真正补到的点：

\- `isalnum()`：判断是不是字母或数字

\- `lower()`：转小写

\- 为什么跳过无效字符要用 `while` 而不是 `if`

\- 为什么 `left += 1`、`right -= 1` 不属于 `if`

\- 为什么 `return False` 是中途拦截，`return True` 是最后通过



我现在对循环的理解有明显进步：

\- `while` 负责不断检查/不断跳过

\- 如果循环中途发现问题，会先 `return False`

\- 如果整个循环安稳结束，就最后 `return True`

我对 704 Binary Search 的当前理解：

\- 二分查找的前提是数组有序（升序）

\- 核心不是一个个找，而是每次看中间，排除一半

\- 需要维护 `left`、`right`、`mid`

\- `mid` 必须写在循环里，因为 `left` 和 `right` 每轮都会变，`mid` 也必须重新计算

\- 如果 `nums[mid] == target`，直接返回 `mid`

\- 如果 `nums[mid] < target`，说明目标在右边，所以 `left = mid + 1`

\- 如果 `nums[mid] > target`，说明目标在左边，所以 `right = mid - 1`

\- 循环结束条件是 `left > right`

\- 如果循环结束还没找到，说明区间已经空了，所以返回 `-1`



我对 35 Search Insert Position 的当前理解：

\- 这题本质是 Binary Search 的变形

\- 前面的二分过程和 704 几乎一样

\- 关键区别只在最后：

  \- 704 找不到返回 `-1`

  \- 35 找不到返回 `left`

\- 我现在已经理解：一开始 `left` 只是左边界，不是先定义成插入位置

\- 通过不断排除不可能的位置，最后在 `left > right` 时：

  \- `left` 左边的元素都 `< target`

  \- `left` 右边的元素都 `> target`

\- 所以 `left` 最后正好停在“小于 target”和“大于 target”的分界点上

\- 因此 35 题最后返回的是 `left`，不是 `right`

我对 69. Sqrt(x) 的当前理解：



\* 这题不是求真正的小数平方根，而是求平方根向下取整的整数部分

\* 本质是在找：最大的整数 `k`，满足 `k * k <= x`

\* 因为 `mid` 越大，`mid * mid` 也越大，所以具备单调性，可以二分

\* 这题不是普通“找目标值”，而是在找边界：最后一个满足条件的位置

\* 当 `mid * mid == x` 时可以直接返回

\* 当 `mid * mid < x` 时不能直接返回，因为右边可能还有更大的合法值

\* 所以需要用 `ans` 记录当前候选答案，再继续往右找

\* 最后返回的是 `ans`，不是随便返回 `left` 或 `right`



我对 1. Two Sum 的当前理解：



\* 这题暴力法是双重循环，但效率低

\* 哈希表适合这题，因为它可以快速查“某个值之前有没有出现过”

\* 对于当前数字 `num`，真正要找的不是任意另一个数，而是 `need = target - num`

\* 哈希表里存的是：数字 -> 下标

\* 遍历数组时，用 `enumerate(nums)` 同时拿到下标和元素

\* 正确顺序是“先查再存”：



  \* 先算 `need`

  \* 先查 `need in seen`

  \* 没找到再 `seen[num] = i`

\* 不能先存再查，否则当前元素可能和自己配对

\* 返回的是两个下标组成的列表，不是数字本身

我对 202. Happy Number 的当前理解：



\* 这题的本质不是数学题，而是“重复变换 + 查重”。

\* 规则固定：把当前数的每一位拆出来，平方后相加，得到下一个数。

\* 同一个数在同一个规则下，下一步结果永远固定。

\* 快乐数规则不会让数字无限变大，反而会把大数迅速压到较小范围内。

\* 因为范围有限，如果一直变不成 1，就迟早会出现重复数字。

\* 一旦某个不是 1 的旧数字再次出现，就说明进入循环，因此不是快乐数。

\* 这题只需要判断“某个数字以前出现过没有”，所以用 `set` 最合适。

\* 主逻辑是：



  \* `n == 1` 时返回 `True`

  \* 否则先查当前 `n` 是否在 `set` 中

  \* 如果在，返回 `False`

  \* 如果不在，就加入 `set`

  \* 再去算下一个数

\* 这题适合“先查后存”。

\* 拆位规则我现在能理解：



  \* `% 10` 取最后一位

  \* `// 10` 去掉最后一位

  \* 直到 `n == 0` 说明拆完了

\* `get_next(n)` 的作用，我现在可以先理解成：专门负责把当前数变成“各位平方和”的下一步数字。

\* `self.get_next(n)` 对我当前阶段来说，可以先理解成“调用 get_next 这个辅助函数”。



我对 217. Contains Duplicate 的当前理解：



\* 这题本质也是查重。

\* 最直接想法可以用 `dict` 计数，但这题只需要判断“是否重复”，所以 `set` 更自然。

\* 主逻辑是：



  \* 遍历 `nums`

  \* 对每个 `num` 先查它是否已经在 `seen` 中

  \* 如果在，说明重复，返回 `True`

  \* 如果不在，就加入 `seen`

  \* 全部遍历完还没重复，就返回 `False`

\* 这题和 Happy Number 的共通点是：



  \* 都是在记录“之前是否出现过”

  \* 都适合 `set`

  \* 都是先查后存

\* 不同点是：



  \* Happy Number：重复说明进入循环，返回 `False`

  \* Contains Duplicate：重复说明数组里有重复，返回 `True`



【今天新补到的 Python 语法点】



1. `set()`：创建空集合，不能写成 `{}`，因为 `{}` 是空字典。
2. `seen.add(x)`：把元素加入集合。

\* `call`：立刻执行，参数一个一个传。

\* `apply`：立刻执行，参数通常按数组传。

## 【我对 125. Valid Palindrome 的当前理解】

### 这题本质是什么

* 这题不是计数题，不是查重题。

* 这题本质是：

  **按题目规则跳过无关字符后，用左右双指针判断是否首尾对称。**

### 我已经理解的核心点

* 要用左右双指针，不是字典计数。
* 空格、标点等非字母数字字符要跳过，不参与比较。
* 大小写要统一后再比较。
* 当左右都已经指向合法字符时：

  * 如果不相等，直接 `return False`
  * 如果相等，左右一起向中间移动
* 如果整个 `while left < right` 都没有出问题，最后再 `return True`

* 这题里不能用三个并列 `if` 去写“跳过左边 / 跳过右边 / 比较左右”。
* 正确结构更适合：

  * `if`：左边不合法，先跳过左边
  * `elif`：右边不合法，先跳过右边
  * `else`：左右都合法，才比较

### 我已经理解的原因

* 三个并列 `if` 会导致同一轮里：

  * 刚跳过字符
  * 又继续比较
* 这样会破坏这题“每一轮只处理一种情况”的节奏。
* 所以这里 `if / elif / else` 的本质是：
  **让每一轮循环只处理一个分支。**

* 外层不是一个个字符扫，而是：

## 【我对闭包的当前理解】

### 闭包最核心的一句话

* 闭包不是一种新语法。

* 闭包更像一种现象：

  **内部函数被带到外部后，仍然能够访问外部函数里的变量。**

---

### 我已经理解的核心点

#### 1. 闭包不是“outer 没结束”

* 我一开始容易误以为：是不是 `outer` 没结束。
* 现在我已经补清：

  * `outer` 的执行其实已经结束了
  * 特殊的是：被内部函数继续引用的变量还在继续被使用

#### 2. 关键不在于“必须 return inner”

* `return inner` 是最常见、最适合当前阶段理解的方式

* 但不是唯一方式

* 真正关键的是：

  **内部函数被带到外部后，还在继续引用外层变量**

#### 3. 不是“count 被带出来了”

* 更准确地说：

  * 被带出来的是函数 `inner`
  * 而 `inner` 还能继续访问 `count`

#### 4. 同一个 `outer()` 返回的函数，会记住那一次的变量

* 我已经理解：

  * `const fn1 = outer()`
  * `const fn2 = outer()`
  * 这两个不是同一个闭包
* 每调用一次 `outer()`，都会形成一套新的闭包环境

## 【Day 10 前端做过的关键实验】

### 1. 计数器闭包实验

```javascript
function outer() {
  let count = 0;

  function inner() {
    count++;
    console.log(count);
  }

  return inner;
}

const fn = outer();
fn();
fn();
fn();
```

#### 我已经理解：

* `fn` 装的是返回出来的 `inner` 函数本身
* 每次执行 `fn()`，本质上是在执行 `inner()`
* `count` 不会每次重置，所以输出 `1 2 3`

---

### 2. 两个闭包互不影响实验

```javascript
const fn1 = outer();
const fn2 = outer();

fn1();
fn1();
fn2();
fn2();
```

#### 我已经理解：

* 输出是 `1 2 1 2`
* 因为：

  * `fn1` 和 `fn2` 是两次不同 `outer()` 产生的结果
  * 它们各自连着不同的 `count`

---

### 3. `console.log` 和 `return` 的区别实验

* 我已经理解：

  * `console.log(count)`：函数内部直接打印
  * `return count`：把结果交出去，再由外面决定怎么处理

---

### 4. 缓存函数闭包实验

```javascript
function outer() {
  let message = null;

  function getMessage() {
    if (message === null) {
      message = "hello";
      console.log("第一次生成 message");
    }

    return message;
  }

  return getMessage;
}
```

#### 我已经理解：

* 第一次执行时：

  * `message` 是 `null`
  * 所以会先生成 `"hello"`

* 第二次、第三次执行时：

  * 直接复用之前的 `"hello"`

* 我现在已经理解：

  * 缓存函数的本质不是“少打印”

  * 而是：

    **第一次生成结果，后面直接复用结果，不重复生成**

---

### 5. `var` + `setTimeout` 的循环坑实验

```javascript
for (var i = 0; i <= 3; i++) {
  setTimeout(function () {
    console.log(i);
  }, 0);
}
```

#### 我已经补清并理解：

* 这不会输出 `0 1 2 3`
* 而会输出 `4 4 4 4`
* 原因不是“for 里有函数就这样”
* 更准确地说：

  * `setTimeout` 里的回调不是立刻执行
  * `for` 会先跑完
  * 当 `i = 3` 那一轮执行完后，还会执行 `i++`
  * 所以循环结束时 `i = 4`
  * 后面 4 个回调执行时，看到的是同一个已经变成 `4` 的 `i`

#### 我还理解了为什么截图里看起来像只输出一个 4

* 因为浏览器 Console 会把重复输出折叠显示
* 右边的重复次数标记表示它实际输出了多次

---

### 6. `let` 版循环实验

```javascript
for (let i = 0; i <= 3; i++) {
  setTimeout(function () {
    console.log(i);
  }, 0);
}
```

#### 我当前已经理解：

* 这次输出会是 `0 1 2 3`
* 我现在可以先这样理解：

  * `var`：多个回调共用同一个 `i`
  * `let`：每一轮更像各自有自己的一份 `i`

### 这部分最核心的一句话

* 对象的方法不一定写在对象自己身上。
* 当对象自己没有某个方法时，它可以沿着原型链继续往上找。

## 【我已经理解的核心点】

### 1. 为什么会需要 `prototype`

* 如果有很多“同类对象”，它们的某些方法逻辑完全一样，就没必要每个对象都复制一份。
* 所以更合理的分工是：

  * 每个对象自己的数据，放在实例自己身上
  * 所有实例共用的方法，放在 `Person.prototype` 上

---

### 2. `name` 为什么适合写成 `this.name = name`

* 因为 `name` 是每个对象自己的数据，不同实例应有不同内容。

* 所以在：

  ```javascript
  function Person(name) {
    this.name = name;
  }
  ```

  里，`this.name = name`` 的本质是：把这次新创建对象自己的 `name` 放进去。

---

### 3. `sayHi` 为什么更适合放在 `Person.prototype`

* 因为 `sayHi` 的逻辑对不同实例来说通常是相同的。

* 如果写成：

  ```javascript
  this.sayHi = function () { ... }
  ```

  那每创建一个对象，就会重新创建一份函数。

* 如果写成：

  ```javascript
  Person.prototype.sayHi = function () { ... }
  ```

  那多个实例可以共享同一份函数。

---

### 4. 我已经分清两类问题不是一回事

我今天重点补清了两个原来容易混的点：

#### 问题 A：函数有几份

* 实例写法：每个对象各有一份函数
* 原型写法：所有对象共享一份函数

#### 问题 B：函数从哪里找

* 先找对象自己
* 自己没有
* 再沿着原型链往上找

我现在已经能区分：

* “函数有几份”
* “函数从哪里找到”

这两个不是一个问题。

---

### 5. `Person.prototype` 和 `p1.__proto__` 的关系

我已经理解：

* `Person.prototype`：更像构造函数那边准备好的**公共方法区**
* `p1.__proto__`：更像 `p1` 这个对象**往上查找的连接**

而在当前例子里：

```javascript
p1.__proto__ === Person.prototype
```

所以它们打印出来看起来一样，但角色不同。

---

### 6. `new` 大概做了什么

我当前已经能用比较稳的方式说明 `new Person("James")` 的大概过程：

1. 创建一个新对象
2. 自动让这个新对象的 `__proto__` 指向 `Person.prototype`
3. 执行构造函数，并让 `this` 指向这个新对象
4. 所以 `this.name = name` 会把 `name` 放到这个新对象自己身上
5. 最后把这个新对象返回出来

---

### 7. 我已经理解 `hasOwnProperty`

我今天补清了：

```javascript
p1.hasOwnProperty("name")
```

和

```javascript
p1.hasOwnProperty("sayHi")
```

的区别。

我已经理解：

* `hasOwnProperty("xxx")` 判断的是：这个属性是不是对象**自己直接有的**
* 不是判断：这个属性最终能不能访问到

所以：

* `name` 是实例自己有的
* `sayHi` 不是实例自己有的，而是从原型上找到的

---

### 8. 我已经理解“先创建实例，后加原型方法”也能生效

我今天补清了一个关键点：

* `new Person(...)` 创建的不是“通向某一个具体方法”的连接
* 而是“通向 `Person.prototype` 这个整个公共区域”的连接

所以即使先创建：

```javascript
const p1 = new Person("James");
```

后面再写：

```javascript
Person.prototype.sayHi = function () { ... }
```

只要最后调用时这个方法已经在 `Person.prototype` 上存在，`p1` 就仍然可以沿着原型链找到它。

## 【我对 242. Valid Anagram 的当前理解】

### 这题本质是什么

---

### 我已经理解的主路线

* 先判断两个字符串长度是否一致
* 若不一致，直接返回 `False`
* 用字典统计第一个字符串中每个字符的次数
* 再遍历第二个字符串，对应字符减 1
* 如果字符不在字典里，或减完后小于 0，直接返回 `False`
* 全程没出问题，最后返回 `True`

### 我已经补清的关键点

#### 1. 为什么不能直接一上来写 `count[ch] += 1`

* 所以要先判断键是否存在

#### 2. 为什么第二个循环要检查两件事

* `ch not in count`：说明第二个字符串里出现了第一个字符串根本没有的字符
* `count[ch] < 0`：说明这个字符虽然存在，但第二个字符串里它出现得更多，数量对不上

## 【我对 56. Merge Intervals 的当前理解】

### 这题本质是什么

* 这题本质上是在做区间的并集整理。

* 关键判断是：

  **后一个区间的左边界，是否小于等于前一个已整理区间的右边界。**

也就是：

```python
current[0] <= result[-1][1]
```

---

### 我已经理解的主路线

* 先按区间左边界排序
* 从左到右扫描区间
* 维护一个 `result`，它表示已经整理好的合并结果
* 每次拿 `current` 去和 `result[-1]` 比：

  * 如果重叠，就更新右边界
  * 如果不重叠，就把 `current` 整个加入结果

---

### 我已经理解的代码顺序

1. 先判断 `intervals` 是否为空
2. 再排序
3. 再初始化 `result = [intervals[0]]`
4. 从 `intervals[1:]` 开始遍历
5. 循环里分“重叠 / 不重叠”两种情况
6. 最后返回 `result`

---

### 我已经补清的 Python / 代码细节

#### 1. `if not intervals`

* 不是在判断“定义是否成立”
* 而是在判断：`intervals` 是否是空列表

#### 2. `intervals[1:]`

* 表示从第二个区间开始，到最后一个区间

#### 3. `result[-1]`

* 是 `result` 列表中的最后一个元素
* 在这题里表示最后一个已经整理好的区间

#### 4. `result[-1][1]`

* 表示最后一个已整理区间的右边界

#### 5. `append(current)`

* 是把整个当前区间加入结果列表最后
* 不是加一个数字

#### 6. `sort()`

* Python 可以直接使用内置排序
* 这里不需要自己手写冒泡排序逻辑

---

### 我已经理解为什么重叠时只改右边界

因为已经按左边界排序了，所以：

* `result[-1]` 的左边界一定更早
* `current` 不可能把左边界再往左推

所以重叠时只需要：

```python
result[-1][1] = max(current[1], result[-1][1])
```

## 【我对 Day 12 前端主线的当前理解】

### 这部分最核心的一句话

**Promise 是一个“未来才会有结果”的对象，用来处理异步任务的最终结果。**

------

## 【我已经理解的核心点】

### 1. Promise 是干什么的

- 它不是结果本身
- 它表示：结果现在还没有，但未来会来
- 这个未来结果可能是成功，也可能是失败

------

### 2. Promise 三种状态

- `pending`：还在等
- `fulfilled`：成功完成，并交出结果值
- `rejected`：失败，并交出错误原因

我已经理解：

- Promise 一开始一定是 `pending`
- 之后只会变成 `fulfilled` 或 `rejected`
- 状态一旦第一次确定，就不会再改

------

### 3. `resolve` 和 `reject`

- `resolve(value)`：把 Promise 变成成功，并交出成功值
- `reject(error)`：把 Promise 变成失败，并交出失败原因

我已经能区分：

- `resolve(...)` 只是把状态定成成功
- `reject(...)` 只是把状态定成失败
- 它们不是“直接打印结果”，而是为后面的 `then / catch` 提供输入

------

### 4. executor 是什么

我已经理解：

- `new Promise((resolve, reject) => { ... })` 里这个函数叫 executor
- executor 会在 `new Promise(...)` 时立刻执行
- 它通常负责启动异步任务，并在合适时机调用 `resolve / reject`

我已经能区分：

- executor 是立刻执行的
- `then / catch / finally` 的回调不是立刻执行的

------

### 5. `then / catch / finally` 的分工

- `then`：处理成功结果
- `catch`：处理失败结果，或者接住链中抛出的错误
- `finally`：不管成功还是失败，最后都会执行

我已经理解：

- `finally` 不是第三条结果分支
- 它更像“收尾动作”
- 它不会替代 `then / catch` 的主职责

------

### 6. 执行顺序上的关键点

我今天补清了 Promise 最容易混的顺序问题：

- `new Promise(...)` 里的同步代码会立刻执行
- `then / catch / finally` 的回调不会立刻执行
- 它们会等当前同步代码先跑完，再执行
- 这也是为什么很多输出顺序题里，Promise 的回调不会插到当前同步代码中间去

------

### 7. 链式 `then`

我已经理解：

- 前一个 `then` 的 `return` 值，会传给下一个 `then`
- 如果 `then` 返回的是普通值，下一个 `then` 直接拿到它
- 如果 `then` 返回的是 Promise，下一个 `then` 要先等这个 Promise 完成

也就是说，我已经开始能把“值的传递”和“Promise 的等待”分开理解。

------

### 8. 错误传播

我已经理解：

- `then` 里 `throw new Error(...)`，后面的成功链会断掉，直接进 `catch`
- `catch` 不只是接 `reject`，也能接住 `then` 里抛出的错误
- `catch` 里如果 `return 一个值`，后面的链可以恢复到成功分支
- `catch` 里如果继续 `throw error`，后面就继续按失败走

------

### 9. `Promise.resolve(...)` 和 `new Promise(...)`

我今天已经补清：

- `Promise.resolve(x)` 更像是调用 Promise 自带的静态方法，快速得到一个成功 Promise
- 它适合把“现成值”包装成 Promise
- `new Promise(...)` 是自己手动创建 Promise 实例
- 它更灵活，能通过 executor 去控制异步任务的执行过程，以及何时 `resolve / reject`

我现在已经能区分：

- 快速包装现成值
- 手动定义 Promise 的运行过程

不是一回事。

## 【我对 144. Binary Tree Preorder Traversal 的当前理解】

### 这题本质是什么

这题要求返回二叉树的**前序遍历**结果。
前序遍历顺序是：

**根 -> 左 -> 右**

------

### 我已经理解的主路线

- 用递归函数处理“以当前节点为根的这棵树”
- 如果节点为空，直接返回
- 如果节点不为空：
  1. 先把当前节点值加入结果数组
  2. 再递归左子树
  3. 最后递归右子树
- 最后返回 `result`

------

### 我今天补清的关键点

#### 1. 为什么这题适合递归

因为左子树和右子树本身还是二叉树，处理规则和整棵树一样。

#### 2. 为什么要先 `append(node.val)`

因为这体现了前序中的“前”——先处理当前节点，再去左和右。

#### 3. 为什么空节点要直接返回

因为空节点已经没有东西可处理了，不能再访问 `node.val`。

#### 4. 为什么最后返回 `result`，而不是 `preorder(root)`

因为 `preorder(root)` 是遍历过程，真正存答案的是 `result`；递归函数本身不是最终结果。

------

## 【我对 56. Merge Intervals 的当前理解】

### 这题本质是什么

这题不是暴力两两乱比，而是：

**先排序，再从左到右扫描，维护一个结果数组。**

------

### 我已经理解的主路线

- 先按区间起点排序
- 从左到右遍历区间
- 看当前区间能不能和结果数组最后一个区间合并
- 如果能合并，就更新最后一个区间的右边界
- 如果不能合并，就把当前区间作为新区间加入结果数组

------

### 我今天已经能说清的关键点

#### 1. 为什么要先排序

因为不排序就没法稳定地从左到右判断“当前区间”和“前面最后一个区间”的关系。

#### 2. 为什么只看 `result[-1]`

因为排序后，当前区间只需要和“结果数组中最后一个已合并区间”比较，就够了。

#### 3. 什么叫能合并

如果当前区间起点 `<=` 上一个区间结尾，就说明有重叠，可以合并。

#### 4. 合并时为什么只更新右边界

因为左边界已经由前一个区间代表了，真正要延伸的是右边界，所以取更大的那个结尾。

------

## 六、Day 13 前端关键理解

### 1. async

我现在知道：

```javascript
async function f() {
  return 123;
}
```

返回的不是普通 `123`，而是 Promise。
本质上接近于：

```javascript
function f() {
  return Promise.resolve(123);
}
```

------

### 2. await

我现在知道：

```javascript
const x = await getData();
```

本质上是在做：

- 调用 `getData()`
- 拿到一个 Promise
- 等这个 Promise 完成
- fulfilled 就把值交给 `x`
- rejected 就直接抛错

------

### 3. 执行顺序

我今天已经开始理解：

> `await` 只会暂停当前 async 函数，不会让外面的同步代码停住。

所以像这种题：

```javascript
async function f() {
  console.log("A");
  const x = await Promise.resolve(10);
  console.log("B", x);
}

f();
console.log("E");
```

输出不会是 `A B E`，而会先有外面的同步输出。

## 三、Day 14 前端关键理解

### 1. Event Loop 第一轮核心规律

我现在最需要记住的主线是：

> **同步代码先执行；同步结束后先清空微任务，再执行宏任务；每执行完一个宏任务，也要再次清空微任务。**

这已经不是只会背“微任务比宏任务早”这么简单，而是开始理解：

- 为什么 `Promise.then` 会比 `setTimeout` 早
- 为什么宏任务里新产生的微任务，会先于下一个宏任务执行
- 为什么微任务之间也有先后顺序

### 2. 调用栈（Call Stack）

我现在可以先这样理解：

> **调用栈就是当前正在执行同步代码 / 函数调用的地方。**

比如：

- `console.log(...)`
- 普通函数调用
- 当前正在执行的同步语句

都可以先理解成是在调用栈里执行。

但要注意：

- 调用栈不等于“所有任务”
- 微任务和宏任务一开始不会直接在调用栈里执行
- 它们要先排队，等轮到时再进入调用栈

### 3. 微任务队列和宏任务队列

我现在已经能初步区分：

#### 微任务

最常见的是：

- `Promise.then`
- `catch`
- `finally`
- `await` 后续恢复执行的代码

#### 宏任务

当前阶段最常见先只记一个：

- `setTimeout`

------

### 4. `await` 和 Event Loop 的关系

我现在已经更清楚了：

> `await` 暂停的是**当前 async 函数的后半段**，不是阻塞整个程序。

也就是说：

- `await` 前面的代码先同步执行
- `await` 后面的代码会被放到后面继续执行

## 六、Day 14 算法核心收获

### 1. 104 最大深度

我现在已经更清楚地理解：

> **`maxDepth(node)` 返回的是：以 `node` 为根的整棵子树的最大深度。**

这句比“从当前节点到最深孩子的距离”更稳，因为它更符合递归函数的本质。

我现在也已经理解：

- 空节点返回 `0`
- 空节点没有深度，所以不能算 1
- 叶子节点最后返回 `1`
- `max(leftDepth, rightDepth) + 1` 里的 `+1`，是在算**当前节点自己这一层**

我当前对这题最重要的理解是：

> 这题是一个**返回值型 DFS / 递归题**，不是单纯遍历一下树，而是让每棵子树把自己的答案往上返回。

------

### 2. 94 中序遍历

我现在已经稳住：

> **中序遍历顺序是：左 -> 根 -> 右**

更重要的是：

> **树的前中后序区别，本质上是 `append(node.val)` 放在什么位置。**

也就是：

- 前序：`append -> left -> right`
- 中序：`left -> append -> right`
- 后序：`left -> right -> append`

我现在已经能理解：

- 中序遍历里，`append(node.val)` 要放在中间
- 如果把 `append` 放最前面，就会变成前序遍历
